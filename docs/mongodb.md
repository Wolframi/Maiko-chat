# Сообщения в MongoDB

Сервер использует MongoDB, когда задан `MONGODB_URI`. Без этой переменной локальная
установка продолжает работать с `data/messages.json`. Настройки в `.env.local`
загружаются и собственным сервером, и командой миграции. URI нельзя добавлять в Git.

```dotenv
MONGODB_URI=mongodb://maiko_app:YOUR_PASSWORD@127.0.0.1:27017/maiko?authSource=maiko
MONGODB_DATABASE=maiko
```

## Первый перенос

1. Установить зависимости: `npm ci` в `site/`.
2. Остановить процесс приложения и сохранить резервную копию всей папки `data/`.
3. Проверить доступность MongoDB и настроить переменные окружения в `site/.env.local`.
4. В `site/` выполнить `npm run messages:migrate -- --apply`.
5. Запустить приложение и проверить `/api/health`: `messageStorage` должен быть
   `mongodb`, а `ok` — `true`.

На старом VPS, где исходники лежат непосредственно в корне проекта, команды
выполняются из этого корня. Миграция не удаляет исходный JSON. Она проверяет
структуру, идентификаторы, содержимое частично импортированной базы и итоговое
количество сообщений. Успешная миграция записывает маркер `json-messages-v1`.
После этого сервер читает только MongoDB: старый JSON не может восстановить
удалённые сообщения. При сбое подключения сервер не переключается на JSON.

## Хранение и эксплуатация

Каждое сообщение хранится отдельным документом в `messages`: идентификатор,
комната, позиция и содержимое сообщения. Индексы обслуживают порядок внутри чата
и поиск ключей повторной отправки. Записи сериализованы; сохраняются только
изменённые документы и удаления, с подтверждением большинства и журналирования.
Сервер явно ставит в очередь добавление, правку, удаление сообщения или очистку
комнаты. Обычная запись больше не строит и не сравнивает полный снимок истории;
нормализация ссылок и копирование выполняются только для изменённых сообщений.
Позиции возрастают внутри комнаты: удаление не перенумеровывает оставшуюся
историю. Правка не создаёт отсутствующий документ, поэтому запоздалая
расшифровка не восстанавливает удалённое сообщение.
Очередь отправляется упорядоченными пакетами до 500 операций. При частичном
сбое исходный пакет повторяется до обработки новых изменений. Снимок всей
истории используется только при явном импорте JSON; файловый режим без MongoDB
по-прежнему сохраняет `messages.json` целиком.
Успешный ответ Socket.IO ожидает завершения записи. Сбой записи отражается в
health check и повторяется автоматически. Корректное завершение процесса
ожидает незавершённые записи; для PM2 нужен `kill_timeout` не меньше 20000 мс.

Ограничение в 200 сохранённых сообщений удалено. При старте MongoDB возвращает
только последнюю позицию каждой комнаты, без содержимого сообщений. История
не сохраняется в общей памяти сервера: открытие чата читает последние 80
видимых сообщений и одну запись для определения `hasMore`. Следующая страница
выбирается по позиции сообщения-курсора. Удалённый или скрытый курсор возвращает
ошибку, а одинаковые временные метки не меняют порядок.

Ответы, повторные отправки, редактирование и реакции используют точечные запросы.
Сводки и непрочитанные сообщения сохраняются в `message_summaries` для пары
комнаты и пользователя. Первое обращение строит сводку из истории; затем
добавления, правки, удаления и служебные изменения обновляют её инкрементально.
Обычная отметка прочтения не требует подсчёта сообщений. Подробности и исключения
для исторических отметок прочтения описаны в [производительности](performance.md).
`message_summary_dirty` отмечает незавершённые изменения: после сбоя процесса
сервер удаляет только затронутые производные сводки и пересоздаёт их по запросу.
Отдельная команда переноса сводок не нужна. Вложения, очистка неиспользуемых
файлов и служебные обновления используют курсоры с порциями по 80 документов;
список вложений держит в памяти только запрошенную страницу. Скрытие истории,
исправление превью ответов и истечение приглашений выполняются через `updateMany`.
Операции одного чата сериализованы, чтобы параллельные реакции и правки не
перезаписывали друг друга. Изменение состава и удаление групп ждут начатые
операции. Сбой запроса возвращается клиенту без остановки серверного процесса.

Для совместимости старый клиент и явный `history:load` с `all: true` пока могут
получить всю историю одной комнаты. Такой ответ временно собирается в памяти
запроса; общей копии всей базы больше нет. Нынешний клиент использует серверный
поиск и небольшие окна вокруг старого сообщения. Файловый режим JSON
продолжает загружать историю целиком.

Пользователи, метаданные чатов, отметки прочтения и закреплённые чаты продолжают
храниться в существующих файлах. Резервировать нужно и MongoDB, и `data/`.
Удалённые прежним лимитом сообщения можно вернуть только из старых копий.

На VPS MongoDB должна слушать только `127.0.0.1`, использовать авторизацию,
постоянный том и автоматический перезапуск. Ежедневный `mongodump --archive --gzip`
нужно сохранять вне контейнера. Проверка восстановления должна использовать
отдельную базу. Старый код, который не поддерживает MongoDB, нельзя развёртывать
поверх мигрированной установки: сначала включить защиту в автообновлении.

## Проверка хранилища

`TEST_MONGODB_URI` должен указывать на тестовый сервер или на пользователя,
которому разрешены создание и удаление временных баз `maiko_test_*`.

```bash
npx tsx --test tests/message-store.test.ts
node --import tsx --test tests/mongodb-pages.test.ts tests/mongodb-history.integration.ts
node --import tsx --test tests/materialized-summary.test.ts tests/mongodb-summaries.test.ts
```

Без `TEST_MONGODB_URI` выполняются проверки очереди с подменённой коллекцией:
одна правка в 10000 сообщений без сериализации остальной истории, стабильные
позиции, изоляция комнат, вложенные изменения во время записи, частичный сбой,
автоматический повтор, очистка без восстановления удалённых сообщений и
завершение процесса с очередью из 1201 записи.

При заданном `TEST_MONGODB_URI` тест дополнительно проверяет перенос 251 сообщения, правки, реакции, альбомы, удаления,
параллельно запланированные записи, повторный запуск, восстановление после
ошибки записи и защиту от повторного импорта удалённых сообщений.

Проверки страниц сравнивают запросы MongoDB с эталоном на 2500 сообщениях:
одинаковые даты, скрытие для разных пользователей, служебные сообщения, сводки,
лимиты выборки и порядок после перезапуска. Интеграционная проверка собственного
сервера использует отдельную временную базу и проверяет старые ответы, правки,
одновременные реакции, закрепления, удаление и независимые копии личной переписки.
Для неё предварительно нужна сборка `.next`.

## Текущий VPS

- Приложение: `/root/maiko/site`, подключение — в `site/.env.local` с правами `600`.
  Каталоги `site/data/` и `site/uploads/` ссылаются на сохранённые
  `/root/pulse-chat/data/` и `/root/pulse-chat/uploads/`.
- MongoDB: контейнер `maiko-mongodb`, том `maiko-mongodb-data`, порт
  `127.0.0.1:27017`, пользователь приложения имеет `readWrite` только в `maiko`.
- Копия до переноса: `/root/backups/maiko-mongodb-20261011T131113Z/`.
- Ежедневные копии: `/root/backups/maiko-mongodb-daily/`; задание —
  `/etc/cron.d/maiko-mongodb-backup`, скрипт —
  `/usr/local/sbin/maiko-backup-mongodb.sh`.
- Защита автообновления установлена в `/usr/local/sbin/pulse-auto-update.sh`.
- Перед публикацией изменений в GitHub остановлены и отключены
  `pulse-auto-update.timer` и `pulse-github-webhook.service`. Это не останавливает
  приложение, MongoDB и ежедневные резервные копии. Автодеплой остаётся отключённым,
  поскольку установленный серверный скрипт пока рассчитан на прежнюю структуру.
  Рабочий сайт перенесён в `site/`; пути PM2, настройки, данные и сборка проверены.
  Перед включением этих служб нужно отдельно адаптировать и проверить серверный
  скрипт автодеплоя. Скрипты в репозитории дополнительно
  отказываются перезаписывать изменённые файлы и автоматически переносить старую
  установку в `site/`.

При переносе проверены все 519 сообщений из 26 исходных комнат. Первая копия
MongoDB успешно восстановлена в отдельную тестовую базу; тестовая база удалена.
Переписка в Electron проверена до и после перезапуска рабочего сервера.
