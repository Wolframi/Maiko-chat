# Проверка Rust: частицы и DAW-аудио

Текущий штатный путь заменён на [готовые бинарные графы и кеш](particle-graphs.md).
Rust/WASM ниже описывает сохранённый резервный расчёт и его прежние замеры.

## Результат

Rust/WASM с текущей обёрткой ускорил построение графа соседей в **1,24–1,34 раза**.
Подготовка с теми же паузами для интерфейса ускорилась в **1,32–1,36 раза**.
Это результат конкретного алгоритма на этой машине, а не ускорение всего Майко.

Для полной модели из 84 000 точек экономия на подготовке составила **109–113 мс**.
Rust подключён к `prepareMaikoDance`: сайт и локальная заставка Electron
используют WASM для подготовки графа. Аудиотракт не меняется.
Исходники находятся в `site/native/particle-graph`, браузерная обёртка —
в `site/src/lib/maikoParticleWasm.ts`. Ниже приведён повторный замер после
подключения текущей обёртки; это не замеры полного запуска приложения.

## Подключение к приложению

- Модуль загружается параллельно с моделью. Первый HTML предварительно загружает
  WASM; URL содержит хеш содержимого и кешируется на год. Общий Promise исключает
  повторные запросы и повторную компиляцию в одном документе.
- В Electron сайт получает модуль из локального набора ресурсов. Заставка окна
  читает фиксированный ресурс через проверяемый `requireShell` IPC, без сети.
- Загрузка и компиляция ожидаются не более 100 мс. При отсутствии WASM,
  сетевой ошибке, таймауте, ошибке ABI или выполнения остаётся прежний JS-путь.
  Подготовка по-прежнему отдаёт управление интерфейсу с бюджетом 4 мс.
- Отмена компонента прерывает только его подготовку, не общую загрузку. Rust
  освобождает граф при завершении/отмене; JS получает собственную копию результата.
- Готовый `.wasm`, файл с его URL и метаданные включены в репозиторий. Обычные
  `dev/build/start` проверяют хеши артефакта и исходников; Rust на сервере не нужен.
  При изменении Rust-кода выполните `npm --prefix site run particles:build`
  и включите обновлённые артефакты в тот же коммит.

## Условия и методика

- Windows x64, Intel Core i5-7600 @ 3,50 GHz.
- Node.js 24.14.1; Chromium 151.0.7922.34 через Playwright 1.62.1.
- Rust 1.95.0, release, `wasm32-unknown-unknown`, без сторонних Rust-зависимостей.
- Реальные `maiko-hiphop.bin` и `maiko-samba.bin`: 14 000, 40 000 и 84 000 точек.
- После первых вызовов — семь замеров, медиана. Порядок JS/Rust чередуется.
- Синхронная пропускная способность и асинхронная подготовка измеряются отдельно.
  Оба асинхронных варианта отдают управление через `setTimeout(0)` при бюджете 4 мс.
- Время Rust включает выделение памяти, копирование входных данных в WASM,
  вызовы через ABI, копирование результата в независимый JS-массив и освобождение.
- Сохранены алгоритм, порядок обхода, разрешение равных расстояний и арифметика f64.
  Сравнивается каждый индекс соседа, а также точное значение `contact`.
- Скачивание модели и WASM, декодирование модели, настройка GPU, отрисовка,
  загрузка React и полный запуск приложения в эти сравнительные времена не входят.

## Остальные вычисления: Node.js, медианы в мс

Это отдельные микробенчмарки существующего JS. Они нужны для выбора участка,
а не для сравнения Rust с JS или измерения сквозной задержки звонка.

| Нагрузка | Время |
|---|---:|
| CPU-симуляция, 14 000 точек, 10 кадров, hiphop / samba | 25,9 / 25,9 |
| CPU-симуляция, 40 000 точек, 10 кадров, hiphop / samba | 85,4 / 82,1 |
| CPU-симуляция, 84 000 точек, 10 кадров, hiphop / samba | 232,2 / 208,9 |
| Форма волны: 5 минут PCM, 8 kHz | 4,0 |
| Разбор DAW: 10 секунд стерео 48 kHz, блоки по два пакета | 1,3 |
| Разбор того же потока с искусственным дроблением по 13 байт | 255,9 |
| Подача данных и DAW worklet: 10 секунд, 44,1 / 48 / 96 / 192 kHz | 10,2 / 10,2 / 12,6 / 18,3 |

CPU-симуляция относится к резервному пути: основной путь уже выполняет
симуляцию на GPU. Штатный Canvas-режим интерфейса ограничен 7 000/14 000
точек; 40 000/84 000 точек на CPU здесь служат проверкой масштабирования.
В аудиозамеры не входят Electron IPC, захват Windows,
работа DAW, кодирование, WebRTC, сеть и джиттер-буферы. Короткие вычисления
не исключают проблем на этих этапах. Блоки по 13 байт — стрессовый сценарий,
а не подтверждённое поведение named pipe в рабочем приложении.

По этим данным первым кандидатом для переноса остаётся подготовка графа.
Аудиотракт стоит менять при подтверждённых задержках/прерываниях в сквозном
профиле. Вычисление формы волны уже занимает мало времени и кешируется.
Для поиска сообщений требуется отдельный профиль запросов MongoDB:
данный эксперимент сервер чата и базу не нагружает.

## Проверки

- Полное совпадение графов для шести сочетаний моделей и плотности,
  включая результаты асинхронной подготовки.
- Пять синтетических случаев: одиночная точка, отрицательные координаты,
  совпадающие позиции, равные расстояния и коллизии пространственного хеша.
- Некорректные размеры входа, заранее отменённый и выполняющийся запрос,
  повторная сборка после отмены.
- Два модульных Rust-теста и `cargo clippy -- -D warnings`.
- Существующие тесты частиц/моделей и DAW, TypeScript и ESLint для файлов эксперимента.
- Production-сборка и проверка защиты JS прошли. Полный набор сайта:
  112 тестов прошли, 3 MongoDB-теста пропущены; настольная часть: 52 теста прошли.
- 11 браузерных проверок загрузки, кеша, анимации, отмены и JS-резерва прошли.
  На настоящей production-странице зафиксировано 1396 вызовов Rust `graph_step`
  для полного графа, без ошибок; MIME и годовой кеш подтверждены HTTP-ответом.
- Сквозной запуск Electron проверен с локальными байтами WASM, обновлением
  интерфейса, отсутствием сети для ресурсов заставки и уменьшенной анимацией.
  Две холодные попытки наткнулись на существующий 15-секундный страховочный
  таймер: создание окна заняло 20–28 секунд и заставка закрылась раньше трёх
  секунд. Последующая проверка прошла с 3024 мс анимации; таймер не менялся.
  Этот эксперимент не устраняет задержки холодной инициализации окна/графики.
  Последующая диагностика, исправление отсчёта таймера и поздней загрузки WASM:
  [холодный запуск Electron](electron-startup.md). В её быстрых запусках
  задержка 20–28 секунд не воспроизвелась.

## Повторный запуск

Из корня репозитория, при установленных npm-зависимостях и Rust:

```powershell
rustup target add wasm32-unknown-unknown
node site/node_modules/playwright/cli.js install chromium --only-shell
npm --prefix site run bench:compute
npm --prefix site run bench:rust
cargo test --manifest-path site/native/particle-graph/Cargo.toml --locked --target-dir output/rust-audit/target
```

Результаты со всеми отсчётами и окружением: `output/rust-audit/baseline.json`
и `output/rust-audit/browser.json`. Каталог `output/` игнорируется Git.
Стенд собирает WASM туда же. Версия для приложения включена в `site/public/wasm/`;
`particles:build` пересобирает её и обновляет хеши/URL, а `particles:prepare`
проверяет их без запуска Rust.
Запускайте замеры без параллельной сборки, тестов и других тяжёлых задач.
Для CPU-профиля вычислительного стенда из `site/`:

```powershell
node --cpu-prof --cpu-prof-dir=../output/rust-audit --cpu-prof-name=baseline.cpuprofile --import tsx scripts/benchmark-compute.mts
```

Профиль относится к искусственно заданной нагрузке стенда. Его распределение
сэмплов не показывает доли CPU в работающем приложении. Текущий отчёт
использует тот же алгоритм; оптимизация структуры данных
или алгоритма может изменить результат как для Rust, так и для JS.
