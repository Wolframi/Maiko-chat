# Защита кода при сборке

Защита включена в обычные production-сборки. Исходники в репозитории и запуск разработки остаются читаемыми.
Это защита от простого копирования и анализа, а не криптографическое шифрование: код, который выполняется на компьютере пользователя, можно исследовать и восстанавливать. Ключи API и другие серверные секреты по-прежнему должны оставаться на сервере.

## Приложение Windows

```powershell
npm ci --prefix desktop
npm run desktop:build
```

Хук `beforePack` в `desktop/package.json` каждый раз создаёт `desktop/.protected/`:

- Модули основного процесса, достижимые из `main.cjs`, проходят `javascript-obfuscator`, преобразование стрелочных функций и компиляцию Bytenode в `.jsc`.
- Компиляция выполняется настоящим основным процессом закреплённого Electron 44.7.0. Использовать системный Node.js или `ELECTRON_RUN_AS_NODE` для этих файлов нельзя: снимки V8 различаются. При смене версии Electron, платформы или архитектуры нужна новая сборка. Выпуск рассчитан на Windows x64 и собирается на Windows x64.
- Preload, служебный процесс локального сервера и JavaScript интерфейса обфусцируются. Preload сохраняет `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`; Bytenode в sandbox не загружается.
- Переносимая функция `contextBridge.executeInMainWorld` и аудиомодули используют профиль без внешних декодеров строк. Для аудиоработы не включены тяжёлые преобразования потока управления.
- Классы `shell.css` и `downloads-panel.css` переименовываются одновременно в CSS, HTML и DOM-операциях JavaScript. ID, IPC, `data-*`, имена файлов и пользовательские строки сохраняются. Стили минифицируются.
- В `app.asar` попадают защищённые файлы и загрузчики байткода. Исходники C#, TypeScript, Rust, тесты, словарь CSS-классов, карты исходников и сборочные скрипты не поставляются. Сторонние runtime-зависимости и публичные ресурсы сайта сохраняются в исходном формате.

Хук `afterPack` проверяет состав `app.asar`, SHA-256 защищённых файлов и соответствие исходникам, использованным при подготовке. Ошибка обфускации, несовместимый компилятор, утечка собственного исходного кода или изменение исходников во время упаковки прерывают сборку. Отчёт `desktop/.protection-report.json` остаётся только у разработчика. Эти проверки контролируют сборку; они не заменяют цифровую подпись установщика.

Проверки:

```powershell
npm --prefix desktop test
# Отдельная тестовая сборка, без замены release/:
cd desktop
npx electron-builder --win --x64 --dir --config.directories.output=test-output/protected-release
npm run test:protection
# Для готового обычного выпуска:
npm run verify:protection
npm run verify:release
```

Локальные CSS/DOM-дополнения, которые работают с загружаемым сайтом (`site-layout.css`, `site-window.css`, `compact-members.js`, `download-progress.js`), сохраняют имена классов сайта: они должны быть совместимы и с уже развёрнутым фронтендом. Их JavaScript обфусцируется. Имена классов локальных окон меняются при каждой упаковке.

## Сайт

```powershell
npm run build
npm --prefix site run verify:protection
```

Production-сборка использует Webpack. `CodeProtectionPlugin` обфусцирует браузерные чанки, содержащие собственные модули из `site/src/`, после минификации и до вычисления итоговых хешей. Чанки только со сторонними библиотеками и runtime Next.js не обфусцируются. Нет `eval`, защиты от отладчика или отключения консоли. Экспорты, публичные свойства и протоколы сохраняются.

Публичные source maps выключены; сборка проверяет их отсутствие и SHA-256 обработанных чанков по `.next/code-protection.json`. Флаг `--turbopack` для production отклоняется, поскольку он обошёл бы Webpack-плагин. Разработка продолжает работать с Turbopack и обычной отладкой. Production-кэш и время сборки отличаются от Turbopack.

CSS сайта минифицируется Next.js. Глобальные классы сайта не переименовываются: их используют SSR, динамические шаблоны, сторонние компоненты и уже установленные Electron-клиенты. Для новых изолированных компонентов можно использовать CSS Modules, которые Next.js именует автоматически.

Bytenode не применяется к браузерному коду или серверу сайта. Серверный код не отдаётся браузеру, а привязка сервера к байткоду потребовала бы закрепить отдельный Node.js/V8 на каждом сервере. Изменения вступают в силу на сайте после развёртывания новой production-сборки, а в программе — после выпуска нового установщика.

Порядок выпуска: сначала разверните защищённую сборку сайта, затем соберите приложение. Подготовка desktop-ресурсов скачивает точные чанки уже работающего сайта; она не изменяет их содержимое и URL. Поэтому ресурсы предыдущего развёртывания в локальном кэше EXE могут ещё содержать прежний минифицированный JavaScript. После обновления сайта новая упаковка получит защищённые чанки автоматически.

Справка: [Bytenode: ограничения Electron](https://github.com/bytenode/bytenode#known-issues-and-limitations), [JavaScript Obfuscator](https://github.com/javascript-obfuscator/javascript-obfuscator).
