# Производительность переписок

## Загрузка медиа

Фото и статические стикеры используют WebP-превью шириной до 430 px,
с сохранением прозрачности. Видео получают отдельную обложку через
`w=430&poster=1`: для показа обложки клиенту не нужен видеопоток.
Если превью недоступно, остаётся загрузка оригинала или штатное видеопревью.

`src/server/mediaPreview.ts` объединяет одинаковые задания, обрабатывает
не более двух одновременно и ограничивает очередь 32 заданиями. Ключ зависит
от имени, ETag оригинала и размера: конвертация видео не оставляет устаревший
кадр. Общий дисковый кеш ограничен 256 МиБ / 2000 превью. Первое обращение
ждёт готовый кадр до 1,2 секунды, затем использует запасной вариант, оставляя
обработку в фоне. При загрузке нового файла подготовка начинается заранее.
S3-файлы ffmpeg читает по временной серверной ссылке с поддержкой Range;
полная временная копия видео для создания обложки не нужна.

Каждое обращение, включая готовое превью и HEAD, проверяет подпись оригинала.
Клиенту не передаётся серверная ссылка S3; ответы сохраняют `private, no-store`.
Фото и обложки начинают подгружаться за 800 px до видимой области. Видимые
картинки получают больший приоритет; анимированные стикеры заранее читают
метаданные и запускают полную загрузку/воспроизведение при появлении на экране.
Giphy отправляется в компактной анимированной версии, а панель выбора
предпочитает уменьшенную частоту кадров превью.

До готовности модели остаётся фон без текста. После подготовки графики
один раз проигрывается сборка модели из точек, которая переходит в танец
без повторной заставки. Подготовка и прогрев скрытых кадров не расходуют
время вступления: оно начинается с отметки 0 и длится 8,15 секунды.
Построение связей между частицами разбито на шаги с
бюджетом около 4 мс, чтобы не блокировать ввод и отрисовку интерфейса.
Сервер заранее выбирает один танец и добавляет preload в первый HTML:
запрос не ждёт гидратации чата.
Встраиваемый интерфейс Electron (`?_desktop_ui=1`) этот preload пропускает,
поскольку модель уже рисует локальное окно приложения.

`npm run models:prepare` создаёт gzip-копии двух моделей перед dev/build/start.
HTTP возвращает `Content-Encoding: gzip`: после распаковки байты совпадают с
оригиналом, детализация не снижается. Размер передачи уменьшается примерно
на 19%. Версионированные URL кешируются на год; при замене исходных моделей
нужно изменить `MAIKO_MODEL_VERSION` в `src/lib/maikoIntro.ts`.
Ошибка или таймаут загрузки переключает на лёгкую модель из `maiko-atoms.bin`
сразу в собранном виде, без повторного скачивания большого файла и второго
ожидания таймаута.

## История сообщений

Клиент объявляет `historyPages: 1` и `chatPatches: 1` в Socket.IO handshake.
Старые клиенты без этих признаков продолжают получать полную историю и событие
`chats` с полным списком. Первоначальная загрузка списка чатов остаётся полной.

При открытии чата новый клиент получает последние 80 видимых сообщений.
`history:load` запрашивает предыдущую страницу по ID первого сообщения, а не
по времени или смещению. Порядок совпадает с сохранённой историей, в том числе
при одинаковых временных метках. Проверка доступа и скрытой истории выполняется
для каждого запроса. Служебные уведомления о входе и выходе исключаются.

При использовании MongoDB страница выбирается непосредственно из базы:
фильтр комнаты и видимости, позиция до курсора, сортировка и лимит 81 запись.
Сервер не загружает всю базу при старте и не хранит переписки в общем массиве.
Отдельные сообщения и ключи повторной отправки ищутся по индексам, сводки
сохраняются в БД. Служебные обходы и вложения читаются курсорами порциями по 80.
Файловый режим JSON сохраняет прежнее хранение в памяти.

Прокрутка вверх подгружает следующую страницу. Кнопка позволяет повторить
неудачный запрос. Запоздалые ответы после переключения чата отбрасываются;
перекрывающиеся страницы сохраняют более свежие изменения уже загруженных
сообщений и исходящие сообщения. Позиция сохраняется по видимому сообщению,
поскольку высота сообщений зависит от текста, медиа и разделителей дней.
При переходе к результату поиска, старому ответу или концу переписки список
удерживает выбранную позицию во время последующего уточнения высот строк.
Колесо, касание и другие действия пользователя освобождают это удержание.

Поиск использует `history:search` с `chatId`, `query` (до 200 символов) и
необязательным `after`. Сервер возвращает до 40 ID, курсор и `hasMore`, без тел
сообщений и общего подсчёта результатов. Поиск сохраняет прежнее совпадение по
подстроке текста, имени автора и имени файла; служебные сообщения и звонки
исключены. Ввод задерживается на 300 мс, устаревшие ответы отбрасываются.
При достижении последнего загруженного совпадения клиент запрашивает следующую
страницу. Счётчик `1/40+` означает, что на сервере есть ещё совпадения.

Переход к незагруженному ответу или результату поиска запрашивает
`history:load` с `around: messageId`: до 40 видимых сообщений перед ним,
само сообщение и до 40 после. Окно заменяет текущую историю, сохраняя исходящие
черновики. `before`/`hasMore` позволяют догружать предыдущие сообщения,
`after`/`hasNewer` — следующие. При прокрутке к нижнему краю окна следующие
страницы подгружаются автоматически, без кнопки «Следующие сообщения» и
перескока к концу добавленной страницы. Кнопка «Вниз» загружает последние 80 сообщений.
Новые сообщения не присоединяются через незагруженный промежуток к старому
окну; собственная отправка возвращает к последним сообщениям. Старое окно
не помечает новые сообщения прочитанными. Большое число непрочитанных также
не вызывает загрузку всей истории. Запрос `all` оставлен для совместимости
старых клиентов, новый интерфейс его не использует.

MongoDB выбирает окна по индексу комнаты и позиции, с ограничением 41/81
запись на курсор. Поиск возвращает только проекцию ID с лимитом 41 и таймаутом
5 секунд. Подстрочный поиск может просматривать много записей комнаты; для
дальнейшего снижения нагрузки БД потребуется отдельный поисковый индекс.
Постоянный кеш — один из следующих этапов.

React Virtuoso отображает только видимые сообщения с запасом. Каждое сообщение
имеет стабильный ключ; при добавлении старой страницы `firstItemIndex`
уменьшается на число добавленных строк одновременно с обновлением данных.
Virtuoso сохраняет измеренные высоты и позицию, включая движение пользователя
во время загрузки. При изменении высоты соседних строк и разделителей видимое
сообщение фиксируется непосредственно перед изменением DOM, а оставшееся
смещение компенсируется после layout-эффектов списка, до отрисовки кадра.
`overscan` обновляет строки порциями, а измерение через
ResizeObserver применяется без дополнительного ожидания кадра.
В режиме уменьшенной анимации длительность и задержка CSS-переходов равны
нулю: ненулевое общее значение создавало переходы даже у технических отступов
виртуального списка и нарушало измерение прокрутки.
Скругления и метаданные соседних сообщений одного автора по-прежнему учитывают
группировку. Обработка метаданных
загруженных сообщений пока остаётся линейной по их числу.

Событие `chat:update` содержит сводку только изменённого чата или `null` для
его удаления из списка. Клиент сохраняет закрепление и сортировку по последнему
сообщению. Расчёт сводки переиспользуется между окнами одного пользователя
только в рамках текущего уведомления.

MongoDB хранит сводки в `message_summaries` отдельно для каждой пары комнаты и
пользователя: количество сообщений, непрочитанные, время прочтения и последнее
видимое сообщение с позицией. Это сохраняет независимые копии личной истории.
Первое обращение к паре строит сводку одной агрегацией; последующие обращения
читают готовый документ. Обычная отметка прочтения обнуляет непрочитанные без
запроса истории. Для исторического времени прочтения или сообщений с будущими
датами остаётся один точный подсчёт непрочитанных при изменении отметки.

Пакет записи читает только прежние версии изменяемых сообщений, применяет
дельты и сохраняет новые сводки. Удаление последнего видимого сообщения требует
одного индексного поиска предшественника для затронутого пользователя.
Скрытие истории, очистка, исправление цитат и истечение приглашений обновляют
сводки в том же цикле записи. Вышедшие из группы пользователи удаляются из
списка обновления сводок; при повторном вступлении сводка создаётся заново.

Перед записью ставится долговечный маркер в `message_summary_dirty`.
Подтверждение отправки ждёт сохранения сообщений и сводок. При частичном сбое
повторяется заранее вычисленный итог, поэтому счётчики не удваиваются.
Уже подтверждённый пакет сообщений не повторяется при сбое записи сводок.
После аварийного завершения сводки комнат с оставшимися маркерами удаляются
и восстанавливаются при следующем обращении из сохранённых сообщений.
Остальные сводки сохраняются при перезапуске. Реплика-сет для этого не требуется;
как и основная очередь сообщений, механизм рассчитан на один процесс записи.
Файловый режим JSON пока использует прежний подсчёт в памяти.

Состояние интерфейса разделено на внешние хранилища: данные сессии и команды,
переписка, список чатов, личный звонок и голосовой канал. Каждый экземпляр
`ChatRuntimeProvider` создаёт собственные хранилища; обработчики соединений
работают в отдельных компонентах. `useSyncExternalStore` подписывает потребителей
на выбранные поля с сохранением ссылки при равных значениях. Серверный снимок
фиксирован, а оболочка монтируется после готовности начальных снимков.

Список сообщений, поле ввода, боковая панель и элементы звонков получают данные
через отдельные подписки. Таймер, индикаторы речи и качество соединения не входят
в подписку оболочки. Её каталог содержит только данные навигации, заголовка и
состава участников: обновления превью и голосовых пользователей не меняют ссылки
этого каталога. Переходы читают свежие счётчики из хранилища непосредственно в
обработчике. Боковая панель сохраняет полные данные чатов и голосовых каналов.
Сообщения и поле ввода используют `memo` и стабильные обработчики.

Разделение ограничивает перерисовки, но не откладывает загрузку кода звонков:
динамические импорты LiveKit, настроек и тяжёлых панелей остаются следующим этапом.
Хук `useChat` пока остаётся единым источником сетевых событий, публикующим
неизменяемые снимки в отдельные хранилища.

Проверки из `site/`:

```powershell
node --import tsx --test tests/history-page.test.ts tests/history-navigation.test.ts tests/message-summary.test.ts
node --import tsx --test tests/history-pages.integration.ts tests/chat-removal.integration.ts
node --import tsx --test tests/message-tasks.test.ts tests/mongodb-pages.test.ts tests/mongodb-history.integration.ts
node --import tsx --test tests/materialized-summary.test.ts tests/mongodb-summaries.test.ts
node --import tsx --test tests/external-store.test.ts tests/chat-catalog.test.ts
npm run build
npx playwright test e2e/state-subscriptions.spec.ts e2e/history-performance.spec.ts e2e/message-scroll.spec.ts e2e/chat-runtime.spec.ts --workers=1
```

Интеграционные и браузерные проверки запускаются после завершения сборки:
их изолированные серверы используют готовую `.next` через junction.
Браузерная проверка использует 2500 тестовых сообщений и проверяет ограничение
числа DOM-элементов, подгрузку, старые ответы, поиск и новые сообщения.
Для тестов MongoDB задайте `TEST_MONGODB_URI` отдельного тестового сервера.
Проверка сводок запрещает обращения к сообщениям при повторном чтении готового
списка, сравнивает результаты с полной историей и моделирует частичные сбои
записи сообщений/сводок и аварийный перезапуск.
Проверка подписок в StrictMode считает вызовы компонентов: 100 обновлений звонка
изолированы от сообщений и списка чатов; 20 последовательных обновлений через
настоящий `ChatRuntimeProvider` с тестовыми источниками не затрагивают оболочку,
сообщения и поле ввода. Проверяются изменения селектора, состав участников,
обновление сообщений и снятие подписок. Отдельная проверка приложения выполняет
личный звонок между двумя изолированными учётными записями с тестовыми медиа,
сворачивание, отключение микрофона и отправку сообщения во время звонка.
